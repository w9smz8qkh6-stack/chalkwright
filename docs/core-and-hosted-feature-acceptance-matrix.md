# Chalkwright Core and Hosted Feature Acceptance Matrix

Status: A01 architecture baseline; implementation has not begun.

This is the authoritative feature-ownership, edition-availability, MVP,
acceptance, and downstream-task matrix for the Core operator panel and the
commercial hosted shell. It freezes product disposition for A01 without
accepting [ADR-0026](decisions/0026-public-core-and-hosted-shell.md), choosing an
implementation mechanism, or authorizing a live effect.

The [A02 threat model](core-and-hosted-threat-model.md) applies the frozen
surfaces and authority boundaries to assets, actors, entry points, abuse cases,
mitigations, residual-risk dispositions, and mandatory negative tests. Later
tasks must satisfy both documents rather than reinterpret the A01 boundary.

## Scope and interpretation

The matrix distinguishes five layers and surfaces:

- **Shared Core behavior/contracts** own edition-neutral domain rules, use
  cases, ports, configuration and display contracts, provider capability
  policy, projections, presentation primitives, and conformance suites.
- **Self-hosted Core shell** owns the one-installation composition, local
  persistence and jobs, private operator ingress, separately bound display
  ingress, direct provider adapters, diagnostics, and independent packaging.
- **Commercial hosted shell** owns accounts, sessions, organizations, roles,
  tenant authorization, hosted persistence and workers, billing, support,
  lifecycle, and authenticated account navigation around shared Core behavior.
- **Classroom display** is the low-privilege, screen-scoped presentation served
  from a committed display projection after viewer admission. It is not an
  operator or account surface.
- **Student/viewer presentation** is a bounded, class-code-admitted projection
  for personal devices. It never receives an internal plan, provider object,
  operator diagnostic, or account record.

An owning layer is the layer that defines and enforces the feature's contract.
Another edition may compose that contract through its own authorization and
adapters without taking ownership of the underlying behavior. Availability in
a column describes the first release of that edition or surface; it does not
claim that the feature is implemented today.

## Status legend

- **Existing** — repository evidence already records the behavior; later work
  must preserve it.
- **Core MVP** — required for the Core operator MVP completion gate.
- **Hosted MVP** — required for the smallest credible hosted MVP described by
  the commercial concept, including one paid screen.
- **Later** — planned after the relevant MVP and assigned to a downstream task.
- **Deferred** — deliberately postponed without an authorized implementation
  tranche; a later human decision and, where noted, a new task are required.
- **Excluded** — intentionally absent from that edition or surface.
- **Not exposed** — supporting behavior may affect the surface, but the feature
  itself and its data are not rendered or callable there.

## Explicit exclusions

A01 freezes these exclusions; a downstream task may not erase them by
implication:

- Core has no Chalkwright user-account, login, organization, role, billing, or
  authenticated operator-session system.
- The Core operator listener is not publicly exposed by default. Repository-
  supplied service and container examples must keep it loopback-only, on a Unix
  socket, or behind an explicitly configured private operator boundary.
- A class code is never operator authorization. It admits only a bounded
  screen/viewer projection.
- Provider OAuth is never Chalkwright login. It authorizes only a selected
  external data connection.
- The hosted shell never starts, proxies, or mounts Core's unauthenticated HTTP
  route table. It composes supported Core use cases and presentation primitives
  below HTTP routing after hosted authentication and authorization.
- Rosters are not imported merely to personalize a display or viewer language.
- The hosted MVP does not host or copy PowerSchool browser profiles.
- The hosted MVP performs no Calendar writes and requests no Calendar write
  scope.
- Automatic translation of classroom content is excluded until a later human
  decision approves provider, privacy, accuracy, retention, cost, and school-
  data handling.
- A01 creates no provider enrollment, billing enrollment, infrastructure,
  repository, package publication, route, deployment, service, credential, or
  other live effect.

## A01 completion statement

A01 is complete because every feature named by its completion condition is
represented by a stable ID with one owning layer; explicit self-hosted, hosted,
classroom-display, and student/viewer availability; a first-release, later,
deferred, or excluded disposition; a concrete authority boundary; observable
acceptance evidence; and downstream task traceability. Specifically, account
management is covered by `ACCT-01`/`ACCT-02`/`ORG-01`; the Core panel by
`PANEL-01`/`PANEL-02`; class codes by `VIEW-01`; source modes by `SRC-01`-
`SRC-03`; Google authorization and connections by `AUTH-01`/`GOOGLE-01`/
`GOOGLE-02`; planned-display review by `PLAN-01`/`PLAN-02`; presentation
profiles by `PRES-01`/`LANG-01`; student personalization by `STUDENT-01`/
`STUDENT-02`; billing by `BILL-01`; and lifecycle by `LIFE-01`/`SUPPORT-01`.

The explicit exclusions and unresolved-decision register prevent A01 from
deciding A02 threat details, A03 packaging, provider enrollment, authentication
or billing vendors, pilot infrastructure, or other live effects. A02 completed
the linked threat model, A03 accepted ADR-0026's implementation mechanics, A04
established the workspace and actor vocabulary, and A05 defined configuration,
persistence, export/backup, migration, and rollback contracts without changing
A01 ownership. A06 through A08 remain required before the architecture-ready
gate is complete and Phase B may begin.
